出典:

- [Building agents: When to fold subagents into your main agent loop（Anthropic）](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop)（公開日 2026-10-22）
- [Anthropic says one AI agent beats many subagents now that models can handle complexity alone（The Decoder）](https://the-decoder.com/anthropic-says-one-ai-agent-beats-many-subagents-now-that-models-can-handle-complexity-alone/)（公開日 2026-10-25）

Anthropic の提案は、仕事をサブエージェントに分けて任せる運用から、一つのエージェントが通しでやる運用（最初から最後まで、一つのエージェントが処理する）への切り替えです。分けていた主な理由は、コンテキスト（モデルが一度に読める量）が足りなくなることでした。必要なときだけ読み込む工夫で、足りなくなりにくくなったからです。分けなくてよくなるうえに、分けることで起きていた受け渡し（エージェントからエージェントへ、結果を要約して渡すこと）の問題も減る、と記事は説明しています。

記事の出所は、次のとおりです。

- 2026 年 10 月 22 日、Anthropic が企業向けの設計記事を公開。書いたのは Diane Sarkis さん
- もとにしたのは、Anthropic の Applied AI チーム（企業の導入を手伝う部署）が現場で見てきたこと
- The Decoder が 10 月 25 日に伝えている
- 示しているのは、サブエージェントを本体に戻し（サブエージェントを無くし、その仕事を本体に取り込むこと）、一つのエージェントが通しでやる考え方と、その手順

あとで何度も出る言葉だけ、先に置いておきます。

- モデル：Claude のような AI そのもの。文章を読んで答えを作る部分
- エージェント：モデルにツールを持たせ、答えが出るまで自分で手順を進める仕組み
- 本体：利用者と会話し、どのサブエージェントを呼ぶかを決める側のエージェント
- サブエージェント：本体から呼ばれる、別のエージェント。自分専用のコンテキスト、ツール、指示を持つ
- コンテキスト：モデルが一度に読める量。指示、会話、ツールの結果がここに入る
- 指示文：画面には出さず、モデルへ渡す「役割と決まり」の文章
- スキル：仕事の手順を書いた文書。名前と概要だけを先にモデルへ渡し、必要なときに全文を読む
- ツール：モデルが外の処理を呼び出す定義。注文を調べる、データを読む、など
- テスト：同じ問題のひとまとまり。記事では評価セットと言う。設計を変える前後で解かせ、どちらが良いかを比べる

### 前は、サブエージェントに分けていた

記事の説明では、分けていた主な理由は、一つのコンテキストに全部が入り切らないことでした。

- 指示、会話、ツールの結果を一つに詰めると、量が膨らむ（増えて、モデルが読める上限に近づく）
- 答えの質が、数字に出るほど（測定すると分かるほど）落ちることがある
- そこで、担当ごとに自分のコンテキストを持つサブエージェントを作り、どれを呼ぶかを決める本体を別に置いていた

大きな企業では、この形がチームの分け方と同じになります。記事は、これが普通の始め方だと書いています。チームごとに作ったエージェントを、呼び出す側の一つのエージェントでまとめる、という始め方にも、それなりの理由はある、と記事は認めています。

- 機能ごとに、作るチームが違う
- 各チームが、自分のエージェントを作る
- 中央のチームが、どのサブエージェントを呼ぶかを決める本体を作る

### 今は、一つで通せるようになった

なぜ今、一つで通せるのか。記事が挙げる理由は 3 つです。

**1. 同じコンテキストを共有した方が、答えが良くなる**

何段階も続く、長い仕事での話です。

- 前の手順の結果が全部手元にあるので、つなげて考えられる
- サブエージェントが返すのは要約だけ。要約を並べるより、元の情報をそのまま使えるので、答えに細かい情報が残る
- 受け渡しの回数も減る

**2. 必要なときだけ読むので、コンテキストが膨らみにくい**

スキルとツールは、短い説明だけ先に見せ、必要になったときに全文を読みます。記事はこれを、分けていた主な理由だった「入り切らない」を起きにくくするもの、と説明しています。

- Anthropic は、新しいモデル向けに Claude Code（Anthropic のモデル Claude を使う、開発者向けのアプリ）の指示文を 8 割超削った
- その削減の一部が、スキルとツールを必要なときだけ読む形への変更

この渡し方を、Claude Code の公式説明で確かめると、こうです。

- セッション開始時に、使えるスキルの名前と概要をコンテキストへ入れる。入れる先はモデル（Claude）で、利用者ではない
- 利用者が見る会話の画面には、その一覧は出ない
- 名前と概要は、依頼のたびに Claude が見ている
- 対象は、最初から用意されているスキルと、利用者が自分で作ったスキル
- 仕事が概要と合うと、Claude が自分で全文を読む。コマンドで指名しなくても進む
- 指名したいときは、スキル名のコマンドを打てば全文が読まれる
- 自分で呼ぶまで動かさない設定にしたスキルは、概要がコンテキストに入らない。最初から用意されているスキルの一部（/verify など）も、自分で呼ぶまで動かない
- スキルが多いと、使う回数が少ないスキルから概要が削られる。名前は全部残る
- Agent Skills（Claude Code 以外の AI ツールでも同じ形で使える、スキルの共通仕様）でも、名前と概要は起動時に指示文（原文ではシステムプロンプト）へ入る

**3. モデル自体が強くなった**

- Anthropic のモデルでは Opus 4.5 以降、一つのエージェントが通しで扱える量が、多くのチームの想定を超えた
- Opus 5.5 と Fable 5.1 は、答える前に内部で考える工程（thinking）を常に使う。切ることはできない
- 最近のモデルは、どこまで進んだかを自分で言葉にし、自分の仕事を確かめながら進む
- そのぶん、進み具合の管理や確認のために人が周りに組んでいたプログラムの一部が、要らなくなる、と記事は述べている

### それでもサブエージェントを残す場合

記事は、サブエージェントを残す条件を 3 つ挙げています。いつ残すか、の話です。

- コンテキストが膨らんで答えが悪くなる：一つで通すと、コンテキストが膨らみ、数字に出るほど答えの質が落ちている
- 同時に進める仕事：複数の仕事を同時にやり、それぞれをまっさらなコンテキストで処理し、終わったら中身を残さず捨てたい
- ツールを選べない：一つのエージェントが正しいツールを選べない（ツールが多いと起きやすい）。または、指示どうしが矛盾している

条件とは別に、何に使うと向くか、も 3 つ挙げています。Anthropic 自身も、自社の調査の仕組みなど、多くのエージェントで使い続けていると書いています。

- 結果を確かめる作業
- 同時に進める仕事
- 権限を分けること。サブエージェントごとに、使えるツールや触れるデータを限る

分けるなら、「何の仕事か」ではなく、「ほかの部分からの情報をどれだけ必要とするか」で分けよ、とも言っています。ほかからの情報をほとんど要らない仕事だけを、サブエージェントに渡す、という意味です。例は 3 つです。

- 互いの結果をほとんど使わない、調査の処理
- 他の処理へ渡す情報が少ない、独立した処理
- 処理の中身は読まず、結果だけを確かめる作業

仕事の種類で分けると、受け渡しのたびに細かい情報が落ちる、と記事は書いています。

### 実際の企業で比べたら、どうだったか

まず、サブエージェントを使っていたときに起きていた問題です。各チームが自分のエージェントを作り、どれを呼ぶかを決める本体を別に置くと、大きな企業では次の 5 つが起きると記事は書いています。

- 受け渡しの往復で、細かいところが落ちる。
- チームごとにサブエージェントを作り、似た働きのものが数百個になる。誰が責任者か分からず、品質を揃える基準も無い。
- 指示文に各チームが 1 文ずつ足す。決まりが矛盾し、口調が揃わなくなる。
- 各チームが、自分の担当だけに合わせたテストを作る。全体の責任を持つ人がいない。経営は、各チームの点数を平均した、実態の見えにくい数字で判断する。
- 構造が複雑なぶん、待ち時間が増える。

ある企業では、顧客向けエージェントの中に、専門のサブエージェントが 12 個ほどありました。どのサブエージェントが答えても同じ口調と同じ品質にするのが難しく、待ち時間が利用者の体験を損ねていました。

次に、比べた結果です。Anthropic は、複数の企業導入で 3 つの設計を比べました。

- スキルとツールを、必要なときだけ読む一つのエージェント
- 指示文に、全部を書く設計
- サブエージェントに分ける設計

結果は、こうです。

- 品質では、一つのエージェントがたびたび上回った
- 1 問あたりの費用と待ち時間も、多くの場合で下がった
- ある顧客の自社比較では、実行時間がおよそ 2 倍速くなった。これは 1 社の例
- 比べ方、企業名、どのモデルで比べたかは、公開されていない
- Anthropic の記事なので、Anthropic のモデル（Claude）で比べたと考えるのが自然だが、他社のモデルで同じことが言えるかは分からない

よく見る設計の組み合わせも、記事は挙げています。

- 利用者の意図を分類してから、先の処理へ進む
- 順番が固定された、複数段の処理
- 利用者を区分に分ける
- 区分ごとに、おすすめを出す処理を分ける
- どの処理を呼ぶかを決めるエージェントを、別に置く

この組み合わせについての、記事の見立ては、こうです。

- この構造の大半は、モデルがもう自分でできる仕事を、代わりにやっていた
- 次の 3 つが揃えば、用途の大半は足りる。はっきりした指示が 1 つ。データを読み取るだけのツールが 4〜5 個。答えが決めた範囲を外れないように止める処理

新しいモデルに切り替えるとき、サブエージェントの分け方を固定したままだと、新しいモデルがもっと多くの仕事をこなせるのに、その邪魔になっていることがしばしばあった、と記事は書いています。

### だから今後は、一つで通す形に戻す手順

記事が目指す形は、こうです。

- モデルは一つ。読んでいるコンテキストも一つ
- その中で、必要なツールを呼びながら、最後まで進める

モデルに任せず、プログラム側で固定して残すのは、2 つだけです。

- 何回まで動かしていいか、いくらかけていいか、の上限
- データを書き込む前に、一度止めて確認する仕組み

モデルの判断に任せる形へ移すのも、2 つです。

- 仕事の順番や、分野ごとのやり方は、スキルに書く
- 答えの確かめや、承認は、それを行うツールに持たせる

担当も変えます。

- 指示文と、全体の品質を測るテストは、一つの小さな中央チームが持つ
- 各チームが持つのは、自分専用のエージェントではなく、スキルとツール

戻す順は、3 つです。

1. 先にテストを作る。最初の問いから最後の答えまで、通しで解かせる。10 問でよい、と記事は言っている。このテストで、戻す前と戻したあとを比べる
2. 「残す条件」に当てはまるサブエージェントは、まだ一つに戻さない。本体が、それをツールとして呼ぶ。利用者との会話を進めるのは、本体のまま
3. 残りは 1 つずつ変える。指示はスキルにする。外の仕組みを呼んでいた部分は、ツールにする。同じテストで、変えた場合と変えない場合を比べ、良い方を残す

変えると壊れる例も、記事は載せています。例は、試しに作った顧客サポートのエージェントです。

- サブエージェントを 1 つ、別のサブエージェントにまとめた
- 待ち時間は下がった
- 一方で、それまで通っていた処理が 1 つ壊れた
- 本体が注文を探すツールを自分で持っていたため、届け日を配送担当のサブエージェントに聞かず、自分で答えてしまった
- この壊れ方は、2 回走らせて 1 回しか出なかった

だから記事は、変える前にテストを足すよう求めています。

- 本番で続けて動いている一連の仕事ごとに、1 問
- 破ってはいけない決まりごとに、1 問
- 各問は、複数回走らせる

ツールの数にも注意があります。指示文の中にツールの定義が 30〜50 個を超えると、選び方が悪くなりやすい、と記事は書いています。

- 利用者の目的ごとに、ツールをまとめる
- 全部を先に読まず、探して、必要なものだけ読む

この戻し作業のために、Anthropic が最近公開したスキルは 4 つです。移行キット（single-agent-loop-kit。この 4 つを順に使う手引き）が、一つの手順につないでいます。

- テストを作る
- 古いモデル向けの指示を洗い出す
- テストを見ながら改善を繰り返す
- 費用のかけ方を見直す

### 自分の環境で試すなら

- エージェントを運用している方は、サブエージェントごとに、なぜ分けているかを 1 行で書きます。
- 今も一つにすると困るからなのか。それとも、仕事の種類ごと、または作ったチームごとにサブエージェントを置いているだけなのか。
- 困る、とは上の 3 つです。一つにすると、コンテキストがまだ膨らんで答えが悪くなる。複数の仕事を同時に進め、終わったらそのコンテキストを捨てたい。一つのエージェントが正しいツールを選べない（ツールが多いと起きやすい）、または指示が矛盾する。
- この 3 つのどれでもないものは、本体に戻す候補です。
- 一つに戻すのを試す方は、変える前にテストを作ります。10 問でよい、と記事は言っています。1 問は、利用者の最初の問いから、最後の答えまでを通しで解かせる問題です。途中の作業だけを見る問題ではありません。
- サブエージェントは、全部いっぺんに戻しません。1 つだけ戻して、同じ 10 問を解かせます。戻す前より悪くなった問題がないかを見ます。
- 各問は、2 回以上解かせます。上の顧客サポートの例では、配送担当に聞かず届け日を自分で答えてしまう壊れ方が、2 回のうち 1 回しか出ませんでした。1 回だけだと、見逃します。
- 自分で指示文やスキルを書いている方は、古いモデル向けに足した決まりが残っていないかを見直す価値があります。公開されたスキルの 1 つは、その洗い出しのためのものです。動きを遅くしている決まり、モデルの判断を縛って融通をなくしている決まりを見つけます。

### 参考文献

Claude Code がスキルの名前と概要を渡す仕組みは、次の公式説明で確認しました。

- [Extend Claude with skills（Claude Code Docs）](https://code.claude.com/docs/en/skills)。名前と概要の一覧をコンテキストへ入れ、Claude が使えるスキルを分かるようにする、と書いてあります。最初から入っているスキルと、自分で作るスキルの両方があります。スキルの共通仕様は Agent Skills です。
- [Extend Claude Code（Claude Code Docs）](https://code.claude.com/docs/en/features-overview)。標準では、概要はセッション開始時に読み、全文は使うときに読みます。モデルが自分で呼べるスキルは、名前と概要を依頼のたびに見ます。自分で呼ぶまで動かさない設定は、指定するまで何も読みません。
- [Agent Skills（Claude Platform Docs）](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview)。名前と概要は、起動時にシステムプロンプトへ入ります。スキルが動くまで、コンテキストを使うのは名前と概要だけです。
