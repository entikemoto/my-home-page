### この回の要点（先に読む）

- **変わったこと**: 中島さん・Karpathyさんの知見を取り込むスカウトスキルの「採用基準」を厳格化した。加えて、2025年7〜9月号のメルマガから非エンジニアに本当に使える4原則を追加した
- **いままでとの違い**: 以前は「言い換えれば使えそう」という理由で採用していたものがあった。今回から「Claude Codeが完全に代行できるか」「評価にエンジニア知識が不要か」の2条件を両方満たさなければ採用しないルールにした
- **メリット**: 「中島さんのような超一流エンジニアと同じことをする」という無理な前提の改善案が混入しなくなった。今後の提案はすべて非エンジニアが今日から使えるものだけに絞られる

### 何が変わったか

**スカウトスキルのフィルターを2段階から厳格化**

これまでのフィルターには「○ 翻訳して採用」というカテゴリがありました。「エンジニア向けの知見でも、言い換えれば使えるものは採用する」という考え方です。しかし、今回の見直しで問題が明らかになりました。

たとえば「ターミナルを二窓開いて、コードを書きながら細かくcommitする」という中島さんの実践。これを「Claude Codeも1ステップごとにcommitすればいい」と言い換えて採用提案していましたが、実際には Claude Code がすでにそれをやっており、非エンジニアには何も変わらないルールでした。「翻訳」が形だけになっていた例です。

新しいルールは2問で判定します。

```
Q1: コーディング知識なしに「考え方・哲学」として使えるか？
    → YES なら ◎ そのまま採用

Q2: Claude Code / CLAUDE.md が完全に代行でき、
    結果の判断にもエンジニア知識が不要か？
    → YES なら ○ ブリッジして採用（具体的な仕組みとセットで提案）
    → NO なら × スキップ（「翻訳すれば使える」は理由にならない）
```

このルールで過去に追加した12件を再審査したところ、11件は問題なし。1件（「朝にtmuxでエージェント設定、夜に確認する」ワークフロー）の手順説明がエンジニア向けだったため、「Claude Codeに任せる・`/tmux-guide`を使う」の形に書き直しました。

**7〜9月号から取り込んだ4原則**

どれも「コーディングスキルなしに今日から使える」原則です。

- **AIへの指示は設計＋ステップ分割**: 大きな指示を一度に出してAIに設計させない。設計はオーナーが決め、実装だけを1ステップずつ渡す。一気に大量の食材を渡して「何か美味しいもの作って」と言うより、「今日は和食で、まず出汁を取って」と順番に指示する方がAIは正確に動く
- **コンテキスト設計の原則**: AIに渡す情報は「入れるもの」だけでなく「入れないもの」も選ぶ。机いっぱいに資料を広げても作業効率は上がらない。AIも同じで、余計な情報が多いと精度が落ちる
- **プロトタイプ・ファースト（意思決定編）**: 企画・院内承認・投資家説明の場で「言葉での説明」より「動く画面を触ってもらう」方が意思決定が速い。Claude Codeでバイブコーディングした80点プロトタイプを持参することが承認への最短ルート
- **プロダクトオーナーのAI協働責務**: 「AIを使って何かを作ること」より「AIをどう組み合わせて価値を生み出すかを設計すること」がオーナーの本質的な仕事。任せる範囲が広がるほど、オーナーの判断・方向性の重要度は増す
