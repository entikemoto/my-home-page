# 業務フロー・自動化範囲（Before/After）

> 目的：エンジニアも非エンジニアも「このプロジェクトが業務のどこを変えるか」を数分で把握できるようにする。
> 詳細な部品分解・依存関係・データ設計は `docs/business-and-system-overview.md`（システム設計書）を参照。

## 0. Status
- Status: APPROVED

## 1. 対象の業務（Before：現状）

### 1.1 業務のゴール（何を達成している？）
- CortexFlow2.0 が毎日3本×2回（朝3本、夜3本）のAIニュース解説を生成する
- noteでは1記事として朝3本・夜3本をまとめて配信し、読者にAIニュースの最新動向を伝える
- 過去の発信を資産として積み上げながら、個人ブランドを構築する

### 1.2 登場人物（役割）
- **著者（医師Founder）**: CortexFlow2.0の実行・note配信管理・HPへの反映を行う
- **読者（note/HP/X）**: AIニュースを素早く把握したい、過去記事を探したい、著者のプロフィール・思想を知りたい

### 1.3 業務フロー（手動時代・Before）
> 1行＝1ステップ。時系列で書く。

1. CortexFlow2.0 が朝3本・夜3本の解説記事を生成する
2. note では、3本を1つの記事（朝便・夜便）にまとめて配信する
3. X や Slack でも配信導線を動かす
4. 読者が「この前見たあの記事どこだっけ」と思っても、HPに個別記事がないため探しにくい
5. 過去の個別記事が蓄積されず、有用な資産として見えない
6. 個人のプロフィール・思想・医療AI活動は、HPに集約されていない

### 1.4 現状の困りごと（痛み）
- **個別記事を探しにくい**: note の1記事に3本が入っているため、タイトルや日付から1本を再訪しづらい
- **検索性が弱い**: タグ・カテゴリー・月別アーカイブで記事を絞り込む導線がない
- **過去記事の蓄積が見えない**: 日々の発信は続いているが、資産として一覧しづらい
- **ブランド表現が弱い**: note / X / Slack は配信には強いが、著者のプロフィール・ビジョン・医療AI活動をまとめて見せにくい
- **媒体ごとの役割が曖昧**: どこが記事の正本で、どこが配信面なのかが明確でない
- **HP追加時に運用負荷が増える**: 別の記事データを用意する必要があると運用コストが跳ね上がる

## 2. 変えた姿（After：このプロジェクトが実現していること）

### 2.1 変えないこと（固定）
- CortexFlow2.0 で毎日3本×2回の解説記事を生成する（従来通り）
- note では3本をまとめた朝便・夜便として配信する（従来通り）
- X や Slack の配信導線も既存の方針を維持する（従来通り）
- 読者の探しやすさを優先し、Webアプリケーション化はしない（静的サイト）
- HPは個別記事の正本であり、note へのリンク集ではない

### 2.2 自動化・効率化した業務フロー
| Before の業務フロー | After（どう変える） | 実現する部品 |
|---|---|---|
| ① note で3本をまとめて配信 | ① 従来通り note で3本まとめ配信 | note 側（HPとは無関係） |
| ②-③ 業務の一部を HPでの表現に追加 | ② HP では同じ3本を1本ずつ個別記事として保存・表示する | ③ 個別記事表示 |
| ④-⑤ 探しにくい状況を改善 | ③ タイトル・日付・タグから個別記事を後から探せるようにする | ④ 一覧・アーカイブ導線 |
| ⑥ ブランド表現が弱い | ④ 同じHP内にプロフィール・Vision・医療AI活動をまとめて見せる | ⑤ ブランドページ群 |

### 2.3 成功の定義（非エンジニア判定）
> "現象"で書く

- **成功条件1**: HP `/articles` 一覧に最新の個別記事が表示されている
- **成功条件2**: 読者が記事タイトル・日付・タグから過去記事を探せる（検索・フィルター機能が動く）
- **成功条件3**: 記事詳細ページから、元のニュースURL と note のまとめ記事 URL が分かる
- **成功条件4**: 記事詳細ページから `/about` `/vision` へのリンクが自然に配置されている
- **成功条件5**: Lighthouse（Performance / SEO / Accessibility）が 90点以上である
- **成功条件6**: note 配信後、著者がコマンド1つ（`npm run sync:dev-log` など）で HP に反映できる

## 3. 自動化候補の棚卸し（どこを自動化・効率化したか）

| # | 機能 | 対象 | 期待効果 | 実装状況 |
|---|---|---|---|---|
| A1 | 個別記事データの読み込み | ② 個別記事表示の準備 | 記事データは JSON 形式で構造化。複数回手入力する必要がない | ✅ 実装済み |
| A2 | 記事の静的サイト生成 | ② 個別記事表示 | Next.js SSG で生成・Vercel 配布。運用マシンのスペックに依存しない | ✅ 実装済み |
| A3 | 一覧・タグ・日付での絞り込み | ③ 一覧・アーカイブ導線 | 読者が複数の観点から記事を探せる。キーワード検索にも対応 | ✅ 実装済み |
| A4 | ブランドページの事前用意 | ④ ブランドページ群 | プロフィール・Vision・医療AI活動を常に最新状態で見せられる | ✅ 実装済み |
| A5 | OGP・RSS・SEO 対応 | ① 記事データ周辺 | 記事が X で自動展開される。検索流入を取りやすくなる | ✅ 実装済み |
| A6 | HP と note の導線統合 | ⑤ 媒体導線 | 読者が記事から note のまとめ記事へ、そこから X へと自然に流動 | ✅ 実装済み |
| A7 | Vercel Deploy Hook 連携 | ⑥ CI/CD（運用側） | note 投稿 → HP 自動反映（手作業なし） | 未実装（次フェーズ） |

## 4. Before/After の比較表

| 観点 | Before（現状） | After（このサービス導入後） |
|---|---|---|
| **記事の保存単位** | note の3本まとめが中心 | HP では1本ずつの個別記事として蓄積 |
| **検索性** | 個別記事を探しにくい | タイトル・日付・タグで探せる |
| **媒体の役割** | note / X / Slack に分散 | **HP が個別記事の正本、note はまとめ、X / Slack は配信導線** |
| **ブランド表現** | 発信はあるが集約点が弱い | HP を個人ブランドの母艦にできる |
| **運用負荷** | 記事は note のみ。HP 追加時に別データが必要 | **CortexFlow 出力を HP に流すだけで自動反映（Vercel Deploy Hook 対応予定）** |
